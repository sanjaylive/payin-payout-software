## Summary

- **One API process** sustained **~230 req/s** of mixed traffic: 100 payins/s, 30 payouts/s and 50 read iterations/s. There were **0 errors** and p95 was 156 ms for payins (including 80 ms of simulated provider time), 83 ms for payouts and 13 ms for reads. Above ~290 req/s a single process is CPU-bound and latency queues into seconds.
- **The first scale-out exposed a real bottleneck**, now fixed. With three API processes, Postgres became the limit (6.6 cores). **79% of all database time** went to daily/monthly limit checks that `SUM()`ed the merchant's whole month on every payin. Replacing them with atomic running totals (INDEX_REVIEW.md §3) cut database CPU by ~36% at a higher request rate.
- **Three API processes after the fix** sustained **~410 req/s** with all thresholds met: 180 payins/s, 50 payouts/s, 90 read iterations/s (≈230 money-moving writes per second). p95 was 293 ms for payins, 269 ms for payouts and 30 ms for reads. 4 of 49,203 requests failed, all with Docker connection timeouts on the k6 side.
- **After all runs** (93,061 payments, 26,908 payouts):
  - every journal balances;
  - no non-negative account is below zero;
  - every maintained balance equals the sum of its entries;
  - the new limit counters exactly match the transactions they count.

**1000 TPS has not been demonstrated on this hardware.** The path to it is in §3.

## Where the time goes

**API CPU profile** (`--cpu-prof`, payin creates):
- ~30% in Prisma 7's JavaScript query interpreter and ~8% in the `pg` driver;
- ~4% Redis socket writes;
- the rest spread across Nest, crypto (ULIDs, HMAC, AES-GCM) and JSON.

A payin create issues ~30 SQL statements across auth, idempotency, merchant checks, routing, pricing, risk, the create transaction, the provider attempt, the status transition and the request log. **The cost per request is mostly the number of queries.**

**Database** (`pg_stat_statements`, run 4): the remaining top entries are lock waits, not CPU:
- the per-merchant AVAILABLE row lock for payouts;
- the per-merchant usage row for payins.

With only 4 merchants, each sees ~75 payins/s and ~22 payouts/s. This is the expected per-merchant serialisation (§3).

## 3. Path to 1000 TPS

1. **Horizontal API replicas on separate hosts.** API nodes are stateless (Redis for rate limits, nonces and caches; Postgres for state). Run 4 shows throughput scaling with nodes until a shared resource saturates.
2. **Fewer queries per request.** Prime candidates:
   - cache routing rules, pricing plans and provider rows per process with event-driven invalidation, instead of reading them on every request;
   - fold the API request log into a batched writer.

   Each removed query is ~3% of API CPU on the create path.
3. **PgBouncer (transaction pooling) plus a larger Postgres** on dedicated hardware. Read traffic (lists, reports) can go to a replica.
4. **Per-merchant hot rows.** One merchant's payin limit counter and payout balance lock cap that merchant at a few hundred writes per second. If one merchant needs more:
   - shard the usage counter into N sub-rows, summed on read;
   - accept a Redis pre-check in front of the exact database increment.

   Platform-wide throughput is unaffected, since rows are per merchant.
5. **Run k6 from separate load-generator hosts.** Docker Desktop networking is the first thing to fail here.
